# Roadmap progression and autonomy

The roadmap orders product outcomes. Select new autonomous work only from an
outcome marked ready by the project; do not promote ideas, blocked work, or
items needing a product decision because they are convenient to implement.

If a project explicitly adopts an external task board such as Kanban Lite, that
board may own live actionable task state and card-level execution status. The
project roadmap remains the authority for strategic direction, milestones,
sequencing context, and major outcomes; it need not duplicate every actionable
card. Keep the board and roadmap linked where useful, but do not treat either
one as evidence that implementation or validation occurred.

For a complex outcome, create or update an execution plan before committing to
an approach. Complete the affected production path, validation, documentation,
self-review, and commit before marking the outcome done. Update the roadmap
when evidence changes the real status.

Proceed autonomously on ordinary engineering choices: local structure, private
APIs, tests, error handling, necessary refactoring, and proportionate
verification. Record material internal refinements that could otherwise be
reconsidered later.

Escalate only when repository evidence cannot resolve a change to product
scope, supported platform, user workflow, privacy or security behavior,
commercial behavior, destructive data handling, required credentials, or
contradictory accepted product decisions.
